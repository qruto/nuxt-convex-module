A Vue/Nuxt port of `@convex-dev/better-auth`'s `react` + `nextjs` integration. [Better Auth](https://www.better-auth.com) owns the sessions and the sign-in flows; this integration connects them to Convex and to Nuxt's server layer.

It is **not** a default — exactly as in Convex's upstream integration, where it is a separate package. Install it only if you need it.

:upstream-baseline{source="better-auth"}

## Install

:pm-install{packages="@convex-dev/better-auth@~0.13.0 better-auth@~1.7.16"}

That is the whole setup. The integration auto-enables on the next dev run; there is no `modules` entry to add.

Moving from `@convex-dev/better-auth` 0.12? Follow its [upgrade guide](https://labs.convex.dev/better-auth/upgrading/from-0-12) on the Convex side. Nothing changes in `nuxt.config.ts`.

## Configure

Everything below is optional — set it under the `convex` key in `nuxt.config.ts`:

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `betterAuth` | `boolean \| BetterAuthModuleOptions` | auto-detect | Force the integration on or off. Auto-detection turns it on when `@convex-dev/better-auth` is in your `package.json`. |
| `betterAuth.authClient` | `string` | bundled client | Path to your own auth-client module — see [bring your own auth client](#bring-your-own-auth-client). |
| `betterAuth.crossDomainCallbackRoute` | `string` | `''` (unrestricted) | Restrict one-time-token consumption to a single route — see [cross-domain auth](#cross-domain-auth). |
| `betterAuth.loginPath` | `string` | `/login` | Where the `convex-auth` middleware sends unauthenticated visitors. The one route it never redirects away from. |
| `betterAuth.authRoute` | `string` | `/api/auth` | Where the same-origin Better Auth proxy mounts, and where `convexAuth(event)` fetches the Convex token on the server. Changing it needs your own `authClient` created with the same `basePath` — the bundled client calls `/api/auth`, and the module errors at startup otherwise. |

The Better Auth endpoints live on your Convex deployment's `.site` origin, so `NUXT_PUBLIC_CONVEX_SITE_URL` must be set — see [configuration](/getting-started/configuration#runtime-config).

Convex-side setup (`convex/auth.ts` with `authComponent`, `convex/http.ts` registering the routes, and `convex/auth.config.ts`) is unchanged from [the React guide](https://labs.convex.dev/better-auth/framework-guides/react) of the Convex Better Auth component — the Convex half is framework-independent.

## Use

Installing the package gives you (auto-imported with the default [`convex.autoImports`](/getting-started/configuration#module-options-convex), with `Convex` in each name under `'prefixed'` — `useConvexBetterAuth`, `<ConvexAuthBoundary>`; under `false`, import them from `nuxt-convex-module/better-auth/client` and `convexAuth` from `nuxt-convex-module/better-auth/server`):

- **`useBetterAuth()`** (auto-imported) — the Better Auth session, the Convex token fetcher, and the full Better Auth `client` for sign-in/out and any plugin flows. Its return shape is below.
- **`/api/auth/**`** — a registered same-origin proxy route to your Convex deployment's Better Auth endpoints (route configurable via `convex.betterAuth.authRoute`). The proxy answers `GET`, `HEAD`, `POST` and `OPTIONS`; anything else gets a `405` without reaching the deployment.
- **`convex-auth` route middleware** — opt a page in with `definePageMeta({ middleware: 'convex-auth' })`. Unauthenticated visitors are redirected on both server and client to `convex.betterAuth.loginPath` (default `/login`), with the original destination attached as `?redirect=`. It never redirects away from `loginPath` itself, so there is no loop; on the client it waits for the session to settle first, so a hard refresh of a protected page does not bounce a signed-in user. See [the login page](#the-login-page) for how to consume the query safely.
- **`loadAuthClient()`** (auto-imported) — the Better Auth client, loaded on first use; see [how the client loads](#how-the-client-loads).
- **`resolveAuthRedirect()`** (auto-imported) — validates a `?redirect=` destination before you navigate to it.
- **`usePreloadedAuthQuery()`** (auto-imported) — hydrate an SSR-preloaded authenticated query. It shows the preloaded value until auth settles or a live result arrives, holds the last value while auth reloads, and yields `undefined` for a signed-out user.
- **`convexAuth(event)`** (auto-imported in Nitro server routes; also under the upstream-style alias `convexBetterAuthNuxt`) — a request-scoped authenticated client for server routes. See [authenticated server calls](/guide/server-and-ssr#authenticated-server-calls).

### `useBetterAuth()`

```vue [components/UserMenu.vue]
<script setup lang="ts">
const { user, client } = useBetterAuth()

// Auth flows live on the client, typed by the plugins *your* auth client
// installs — e.g. with `emailOTPClient()`:
// await client.signIn.emailOtp({ email, otp })
// await client.signOut()
</script>
```

| Field | Type | What it is |
| --- | --- | --- |
| `isLoading` | `ComputedRef<boolean>` | The session is still resolving and no token is cached yet. |
| `isAuthenticated` | `ComputedRef<boolean>` | A session exists — or one is resolving and a token is already cached. |
| `user` | `ComputedRef<BetterAuthUser \| null>` | `session.data.user`, or `null` while loading or signed out. |
| `session` | `BetterAuthSession` | Better Auth's own `useSession()` ref: `{ data, isPending, error }`. |
| `client` | `AuthClient` | The full Better Auth client — every sign-in, sign-out and plugin flow lives here. There is no `signIn` on the service itself. Until the client has [loaded](#how-the-client-loads), a call through it (`client.signOut()`) loads it first and resolves with the call's result, and a hook (`client.useActiveOrganization()`) answers at once with a pending ref that follows the real one. |
| `fetchAccessToken` | `AuthTokenFetcher` | The Convex token fetcher the client plugin wires into `setAuth`. |
| `authVersion` | `ComputedRef<string \| null \| undefined>` | The session id (or user id), `null` when signed out and `undefined` until the session settles. Moving from one session to another re-registers auth on the Convex client. |

`useBetterAuth(initialToken?)` takes one optional argument, the token the server plugin prefetched. The client plugin passes it; you never need to.

Auth *state* — `isLoading` / `isAuthenticated`, and the `<Authenticated>` / `<Unauthenticated>` components — comes from the provider-agnostic core and is documented under [Auth State](/guide/auth-state).

### The login page

The `convex-auth` middleware sends unauthenticated visitors to `loginPath` with the page they wanted in `?redirect=`. Send them on with `resolveAuthRedirect()` rather than the raw query — it returns the destination only when it is a same-origin path, so a crafted `/login?redirect=https://evil.example` can't turn your login page into an [open redirect](/getting-started/security#post-sign-in-redirects):

```vue [pages/login.vue]
<script setup lang="ts">
const route = useRoute()
const { client } = useBetterAuth()
const email = ref('')
const password = ref('')

async function onSubmit() {
  await client.signIn.email({ email: email.value, password: password.value })
  await navigateTo(resolveAuthRedirect(route.query.redirect))
}
</script>
```

Pass your own landing page as the second argument when `/` isn't right: `resolveAuthRedirect(route.query.redirect, '/dashboard')`.

### Server rendering

During SSR the auth state the module provides is a stub: `isLoading` is `true`, `isAuthenticated` is `false`. So server HTML contains what `<AuthLoading>` renders and nothing from `<Authenticated>` or `<Unauthenticated>`; `useConvexAuth()` reads as loading for the whole server render, and the real state arrives with hydration. Expect a short loading state before signed-in content appears, and don't rely on `<Authenticated>` for content that must be in the initial HTML.

`useBetterAuth()` reads the session side instead. On the server it takes the token the server plugin prefetched for this request, so a signed-in visitor's render reads `isAuthenticated: true` and `isLoading: false`, the same state the browser hydrates with. That makes a "Sign in" or "Open the app" link safe to render on the server. `session` stays pending and `user` stays `null` until the browser loads the session, so render the person's own details on the client.

Signed-in data *can* be server-rendered — through the request, not the session: `convexAuth(event)` on the server, then `usePreloadedAuthQuery()` or `useAsyncQuery()` in the component. The server plugin prefetches the Convex token for the request so those calls run authenticated. See [authenticated server calls](/guide/server-and-ssr#authenticated-server-calls).

### How the client loads

The Better Auth client is not in your app's entry chunk. The module reaches `#convex/auth-client` only through a dynamic import, the first time something needs the client, and keeps that chunk off the `<link rel="prefetch">` list Nuxt writes, so a page that never needs it never downloads it.

- **A signed-in visitor**, or one the server could not check (a prerendered page, a client-only render, a failed token prefetch): the client loads at startup, beside the page rather than in front of it.
- **A visitor whose request carried no session cookie**: nothing loads. The session reads pending while the page hydrates, as the server rendered it, then settles signed out. The client loads on its first use: a call through `useBetterAuth().client`, `loadAuthClient()`, a forced token request, a page behind the `convex-auth` middleware (which decides on the client's own answer), or the tab coming back into view (when Better Auth would refetch the session anyway, so a sign-in in another tab still shows up).
- **A page other visitors may be served** (a `cache`, `swr`, `isr` or `prerender` route rule, or a `Cache-Control` with `public` or `s-maxage`): the client loads at startup. A cached render never saw the visitor's cookie, so it cannot tell anyone they have no session.
- **A cross-domain sign-in**: a `?ott=` token loads the client before startup finishes, to exchange it (the token leaves the address first, so the chunk request never carries it); a session the cross-domain plugin saved in `localStorage` or `sessionStorage` loads it at startup. Storage of your own making is invisible to the check, so the client then waits for its first use, and a page behind `convex-auth` still asks it before deciding.

Code that needs the client itself awaits it:

```ts
async function signOut() {
  const client = await loadAuthClient()
  await client.signOut()
}
```

There is still one client: `loadAuthClient()`, `useBetterAuth().client` once loaded, and a static `import { authClient } from 'nuxt-convex-module/better-auth/client'` all hold the same instance, and the session follows it whichever way it arrived. The static import puts Better Auth in the chunk of every page that imports it, which is the right call for a sign-in page and the wrong one for a layout.

Before the client has loaded, `useBetterAuth().client` forwards: a call waits for the load and resolves with the result, a `use*` hook answers at once with a pending ref that follows the real one, and `useSession(useFetch)` answers with a promise, as Better Auth's does. Any other member read synchronously (`$store`, `$fetch`, a plugin's atom) is a forwarding function until then, so await the client first:

```ts
const client = await loadAuthClient()
client.$store.notify('$sessionSignal')
```

### Bring your own auth client

By default the integration ships a minimal Better Auth client carrying only `convexClient()` — the one plugin the Convex integration itself requires. This mirrors `@convex-dev/better-auth`'s React integration, where you author the `authClient` (with whatever plugins your app uses — OTP, passkeys, …) and pass it to `ConvexBetterAuthProvider`; here you point the module at your own module instead.

```ts [app/convex-auth-client.ts]
import { createAuthClient } from 'better-auth/vue'
import { convexClient, crossDomainClient } from 'nuxt-convex-module/better-auth/client'

export const authClient = createAuthClient({
  plugins: [convexClient(), crossDomainClient()], // add the plugins you need
})
export type AuthClient = typeof authClient
```

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  convex: { betterAuth: { authClient: './app/convex-auth-client' } },
})
```

The aliased client backs `useBetterAuth()`, the client plugin (session wiring and cross-domain token consumption), and the `AuthClient` type of `<AuthBoundary>`'s `authClient` prop — the boundary still takes the client instance as a required prop. The server SSR plugin doesn't touch it at all: it prefetches the token over HTTP via `convexAuth(event).getToken()`.

### Cross-domain auth

Adding `crossDomainClient()` enables cross-domain auth: on landing, `consumeCrossDomainOneTimeToken()` (called automatically by the client plugin) exchanges a `?ott=…` one-time token for a session. Leave it out for same-origin apps — the default client keeps cookies on the same origin.

::warning
By default the one-time token is consumed from the URL on *any* page load and is not bound to the browser that started the sign-in flow — that is the cross-domain design, mirrored faithfully here. Tokens are single-use and expire in ~3 minutes, but while one is live it completes sign-in on whatever page receives it. Only enable `crossDomainClient()` when you actually serve auth across origins, and prefer the same-origin default (cookie sessions, no URL tokens) everywhere else.

When you do enable it, restrict token consumption to the one route your sign-in flows redirect to:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  convex: {
    betterAuth: {
      authClient: './app/convex-auth-client',
      crossDomainCallbackRoute: '/auth/callback', // ?ott= is ignored (and scrubbed) everywhere else
    },
  },
})
```

Point every `callbackURL` you pass to sign-in calls at that route. An `?ott=` link to any other page is then scrubbed without being exchanged, keeping sign-in completion to a single predictable URL.
::

## `<AuthBoundary>`

::callout{icon="i-lucide-flask-conical"}
Experimental — upstream marks it so, and it may change in a minor release. See [experimental symbols](/getting-started/introduction#experimental).
::

Redirects unauthenticated users reactively, and clears an invalid session before redirecting. It watches auth state on mount and on change, and doubles as an error boundary: an auth error thrown below it triggers the same redirect instead of propagating.

```vue [app.vue]
<script setup lang="ts">
import { authClient } from 'nuxt-convex-module/better-auth/client'
import { api } from '#convex/api'
import { isAuthError } from '~/utils/auth' // your own predicate
</script>

<template>
  <AuthBoundary
    :auth-client="authClient"
    :get-auth-user-fn="api.auth.getAuthUser"
    :is-auth-error="isAuthError"
    :on-unauth="() => navigateTo('/login')"
  >
    <slot />
  </AuthBoundary>
</template>
```

| Prop | Type | Default | Purpose |
| --- | --- | --- | --- |
| `on-unauth` | `() => void \| Promise<void>` | required | Called once the session is confirmed invalid — typically a redirect to your login page. |
| `auth-client` | `AuthClient` | required | The Better Auth client instance. Called to clear cookies before `onUnauth` runs. |
| `get-auth-user-fn` | `FunctionReference<'query'>` | required | A zero-argument Convex query returning the user, so the check stays reactive to provider-level auth state. Comes from `export const { getAuthUser } = authComponent.clientApi()` in your deployment. |
| `is-auth-error` | `(error: unknown) => boolean` | required | Your predicate for "this error means unauthenticated". Auth errors are handled and stop propagating; everything else keeps propagating. |
| `render-fallback` | `() => VNode \| null` | `() => null` | Rendered while unauthenticated. Usually left alone, since the handling is a redirect. |

Only the `<AuthBoundary>` component itself is auto-registered — `authClient` must be imported (the export resolves through the `#convex/auth-client` alias to your configured client, so it's the same instance `useBetterAuth().client` returns), and `isAuthError` is your own error predicate.
