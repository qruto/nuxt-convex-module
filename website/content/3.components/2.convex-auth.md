A Vue port of `@convex-dev/auth/react` and a Nuxt port of `@convex-dev/auth/ssr/nextjs`. [Convex Auth](https://docs.convex.dev/auth/convex-auth) keeps users and sessions in your Convex deployment, so there is no separate auth service. The port binds the package's own session engine, `@convex-dev/auth/browser`, to the provider-agnostic [Convex auth state](/guide/auth-state).

:upstream-baseline{source="convex-auth" entry="@convex-dev/auth/react + ssr/nextjs"}

## Install

:pm-install{packages="@convex-dev/auth"}

The client auto-enables on the next dev run. `@convex-dev/auth` needs `convex` 1.48 or newer.

## Configure

Set up the Convex side as [Convex Auth's guide](https://docs.convex.dev/auth/convex-auth) describes: the component in `convex.config.ts`, and an `auth.ts` that exports `refreshSession`, `signOut`, `isAuthenticated` and the functions of each sign-in method. Nothing is required in `nuxt.config.ts`. Set `convex.convexAuth: false` only to force the client off.

## Choose where the session lives

| | Browser storage | Cookies |
| --- | --- | --- |
| The refresh token | in `localStorage` | in an `httpOnly` cookie the page's scripts cannot read |
| The server | never sees the session | renders signed-in data, and your server routes know the user |
| Setup | one call in `app.vue` | one file in `server/` |

Use cookies for an app that renders on the server. The two do not mix: with the server file in place, do not call `provideConvexAuth`.

## Browser storage

Call the composable in a top-level component, above anything that reads Convex data:

```vue [app.vue]
<script setup lang="ts">
import { api } from '~~/convex/_generated/api'

// A Vue port of `<ConvexAuthProvider>`.
provideConvexAuth({
  api: {
    refreshSession: api.auth.refreshSession,
    signOut: api.auth.signOut,
    isAuthenticated: api.auth.isAuthenticated,
  },
})
</script>

<template>
  <Authenticated>Signed in</Authenticated>
  <Unauthenticated>Sign in</Unauthenticated>
</template>
```

The provider stores the session, refreshes the access token before it expires and shares the session between tabs. It also subscribes to `isAuthenticated`, so a session revoked on the server signs the browser out without waiting for the token to expire.

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `api` | `ConvexAuthApi` | required | The app's `refreshSession`, `signOut` and `isAuthenticated` references. |
| `client` | `ConvexVueClient` | the injected client | Override the Convex client to authenticate. Upstream requires it. |
| `storage` | `TokenStorage` | `localStorage` | Where the tokens are kept. |
| `storageNamespace` | `string` | the deployment URL | Tokens are shared between clients with the same namespace. |
| `ambientSignIns` | `AmbientSignInClient[]` | `[oauth()]` | Advanced: sign-in methods that act on page load. |

`<ConvexAuthProvider>` is the same call as a wrapper component, with the options as props.

## Cookie sessions and server rendering

Create one file. Its default export is what switches cookie sessions on:

```ts [server/convex-auth.ts]
import { api } from '#convex/api'

export default setupConvexAuthNuxt({
  refreshSession: api.auth.refreshSession,
  signOut: api.auth.signOut,
  isAuthenticated: api.auth.isAuthenticated,
  // Every function that can start a session. Anything not listed is refused.
  signIn: [
    api.auth.signInWithUsernamePassword,
    api.auth.signUpWithUsernamePassword,
  ],
})
```

`nuxt dev` restarts by itself when the file is created or deleted. The module then does the rest:

- It mounts `POST /api/_convex/auth/signin`, `/refresh` and `/signout`. The sign-in composables call the first one, so the refresh token goes straight into a cookie.
- It refreshes a session that is about to expire before each render and each server route.
- It starts the client for you. There is no provider to call, and `useAuthActions()` and the sign-in composables work in every component, `app.vue` included.

Signed-in data renders on the server with no extra code, because [`useAsyncQuery`](/guide/server-and-ssr) sends the session's token:

```vue [pages/index.vue]
<script setup lang="ts">
import { api } from '~~/convex/_generated/api'

const { data: user } = await useAsyncQuery(api.users.loggedInUser, {})
</script>
```

A page rendered for a signed-in visitor answers `Cache-Control: private, no-store`, because it carries that visitor's token.

In your own server routes, import the file and ask it:

```ts [server/api/me.get.ts]
import { api } from '#convex/api'
import auth from '../convex-auth'

export default defineEventHandler(async (event) => {
  if (!await auth.isAuthenticatedNuxt(event)) {
    throw createError({ status: 401 })
  }
  const token = await auth.convexAuthNuxtAccessToken(event)
  return fetchQuery(api.users.loggedInUser, {}, { token: token! })
})
```

`isAuthenticatedNuxt(event)` asks your deployment, so a forged cookie does not pass. `convexAuthNuxtAccessToken(event)` only reads the token, for calls that the deployment verifies anyway.

| Option | Type | Default | Purpose |
| --- | --- | --- | --- |
| `refreshSession`, `signOut`, `isAuthenticated` | function references | required | The app's functions from `convex/auth.ts`. |
| `signIn` | function references | required | The functions the sign-in route may call. |
| `convexUrl` | `string` | the module's deployment URL | Override the deployment the server talks to. Upstream requires it. |
| `cookieOptions` | `{ secure?, path?, domain? }` | `secure` outside `nuxt dev` | Attributes of the two auth cookies. |
| `allowedOrigins` | `string[]` | none | Extra origins the routes accept, for a proxy that rewrites `Host`. |

During a server render the auth state reads as loading, as in Next.js, so `<Authenticated>` content appears once the browser has connected. Render signed-in data through `useAsyncQuery` instead.

To change the browser side, create `app/convex-auth.ts`. Its default export takes the `storage` and `ambientSignIns` options of [browser storage](#browser-storage):

```ts [app/convex-auth.ts]
import type { ConvexAuthNuxtClientOptions } from 'nuxt-convex-module/convex-auth/client'

export default {
  // Only the access token is stored; the refresh token stays in the cookie.
  storage: import.meta.client ? window.sessionStorage : undefined,
} satisfies ConvexAuthNuxtClientOptions
```

The file is imported on the server too, so check for `window` before using it.

### Protect a page

With cookie sessions the module registers a `convex-auth` route middleware:

```vue [pages/dashboard.vue]
<script setup lang="ts">
definePageMeta({ middleware: 'convex-auth' })
</script>
```

A visitor who is not signed in goes to `/login?redirect=/dashboard`. On a server render the middleware asks your deployment whether the session is valid, so the page's HTML is never sent to a signed-out visitor. On a navigation in the browser it reads the auth state. Change the path with `convex: { convexAuth: { loginPath: '/sign-in' } }`.

On the login page, send the visitor on with `resolveAuthRedirect()`, not with the raw query. It returns a path on your own site, or `/` for anything else:

```ts
const result = await signIn({ username: username.value, password: password.value })
if (result.status === 'complete') {
  await navigateTo(resolveAuthRedirect(useRoute().query.redirect))
}
```

To send a signed-in visitor away from the login page, use `convex-auth-guest` there. It goes to the page's `?redirect=` path, checked by `resolveAuthRedirect()`, or to `/`:

```vue [pages/login.vue]
<script setup lang="ts">
definePageMeta({ middleware: 'convex-auth-guest' })
</script>
```

The middleware runs on a navigation. A visitor who signs out stays on the page they are on, so navigate after `signOut()` if the page should not stay open.

A prerendered page has no visitor, so the middleware would prerender the redirect. Keep protected pages out of prerendering.

## Sign in with a username and password

With browser storage, use these composables in a component below the one that calls `provideConvexAuth`. With cookies, use them anywhere:

```vue [components/LogIn.vue]
<script setup lang="ts">
import { api } from '~~/convex/_generated/api'

const { signIn, pending } = useSignInWithUsernamePassword(api.auth)
const username = ref('')
const password = ref('')
const failed = ref(false)

async function onSubmit() {
  const result = await signIn({ username: username.value, password: password.value })
  failed.value = result.status !== 'complete'
}
</script>

<template>
  <form @submit.prevent="onSubmit">
    <input v-model="username" name="username" autocomplete="username" required :disabled="pending">
    <input v-model="password" name="password" type="password" autocomplete="current-password" required :disabled="pending">
    <button type="submit" :disabled="pending">Log in</button>
    <p v-if="failed">Wrong username or password.</p>
  </form>
</template>
```

`signIn` never throws. It resolves to `{ status: 'complete' }` or to `{ status: 'error', userError }`, and a network or server failure arrives as `userError.error === 'OTHER_ERROR'` with the thrown value on `cause`. `useSignUpWithUsernamePassword(api.auth)` has the same shape and returns `signUp`.

## Sign in with an email and password

Seven composables, one for each step. The ones that start a step return a function and `pending`, as above. The ones for a page that an emailed link opens return a ref of the page's state.

| Composable | What it does |
| --- | --- |
| `useSignInWithEmailPassword(api.auth)` | `signIn({ email, password })`. Signs the visitor in. |
| `useSignUpWithEmailPassword(api.auth)` | `signUp({ email, password })`. Sends the validation email. It does not sign in. |
| `useCompleteSignUpWithEmailPassword(api.auth, { emailCode })` | On the page the validation link opens: confirms the address and signs the visitor in. |
| `useStartPasswordRecovery(api.auth)` | `startPasswordRecovery({ email })`. Sends the reset link. |
| `useCompletePasswordRecovery(api.auth, { emailCode })` | On the page the reset link opens: checks the link, then sets the new password and signs in. |
| `useStartChangeEmail(api.auth)` | `startChangeEmail({ newEmail, currentPassword })`. Sends the confirmation link to the new address. |
| `useCompleteChangeEmail(api.auth, { emailCode })` | On the page the confirmation link opens: applies the new address. |

A link works only in the browser that asked for it. The composable that starts a step keeps a secret in that browser's storage, and the page the link opens presents the secret with the code from the link. In another browser the state is `{ status: 'error', userError: { error: 'MISSING_SECRET' } }`: tell the visitor to open the link where they started.

The page a validation link opens:

```vue [pages/validate-email.vue]
<script setup lang="ts">
import { api } from '~~/convex/_generated/api'

const route = useRoute()
const state = useCompleteSignUpWithEmailPassword(api.auth, {
  emailCode: () => String(route.query.code),
})

watch(state, async ({ status }) => {
  if (status === 'complete') await navigateTo('/')
})
</script>

<template>
  <p v-if="state.status === 'loading'">Validating…</p>
  <p v-else-if="state.status === 'error'">This link cannot be used: {{ state.userError.error }}</p>
</template>
```

The page a reset link opens asks for the new password only once the link has passed its check:

```vue [pages/reset-password.vue]
<script setup lang="ts">
import { api } from '~~/convex/_generated/api'

const route = useRoute()
const state = useCompletePasswordRecovery(api.auth, {
  emailCode: () => String(route.query.code),
})
const newPassword = ref('')
const error = ref<string | null>(null)

async function onSubmit() {
  if (state.value.status !== 'ready') return
  const result = await state.value.completePasswordRecovery({ newPassword: newPassword.value })
  error.value = result.status === 'error' ? result.userError.error : null
}
</script>

<template>
  <p v-if="state.status === 'loading'">Checking the link…</p>
  <p v-else-if="state.status === 'error'">This link cannot be used.</p>
  <form v-else-if="state.status === 'ready'" @submit.prevent="onSubmit">
    <input v-model="newPassword" type="password" autocomplete="new-password" required :disabled="state.pending">
    <button type="submit" :disabled="state.pending">Reset password and sign in</button>
    <p v-if="error">{{ error }}</p>
  </form>
</template>
```

An error about the password keeps the form, so the visitor can try another one with the same link. An error about the link ends the flow.

With [cookie sessions](#cookie-sessions-and-server-rendering), list the three functions that start a session in `signIn`: `signInWithEmailPassword`, `completeSignUpWithEmailPassword` and `completePasswordRecovery`. The others do not start one and go to your deployment directly.

On the Convex side the method sends its emails through the [Resend component](https://www.convex.dev/components/resend), and its setup names the pages the links point at.

## Sign in with a magic link

The visitor types an email address and gets a link that signs them in. There is no password, and the same form serves a visitor who has an account and one who has none. Needs `@convex-dev/auth` 2.1 or newer.

| Composable | What it does |
| --- | --- |
| `useSendEmailMagicLink(api.auth)` | `sendMagicLink({ email })`. Sends the link. It does not sign in, and it answers the same whether the address has an account or not. |
| `useSignInWithEmailMagicLink(api.auth, { emailCode })` | On the page the link opens: signs the visitor in, and creates the account when the address is new. |

The form:

```vue [pages/login.vue]
<script setup lang="ts">
import { api } from '~~/convex/_generated/api'

const { sendMagicLink, pending } = useSendEmailMagicLink(api.auth)
const email = ref('')
const sent = ref(false)
const error = ref<string | null>(null)

async function onSubmit() {
  const result = await sendMagicLink({ email: email.value })
  sent.value = result.success
  error.value = result.success ? null : result.userError.error
}
</script>

<template>
  <p v-if="sent">We sent a sign-in link to {{ email }}.</p>
  <form v-else @submit.prevent="onSubmit">
    <input v-model="email" name="email" type="email" autocomplete="email" required :disabled="pending">
    <button type="submit" :disabled="pending">Continue with email</button>
    <p v-if="error">Could not send the link: {{ error }}</p>
  </form>
</template>
```

`sendMagicLink` never throws. It fails with `INVALID_EMAIL`, with `RATE_LIMITED` and a `retryAfterMs`, or with `OTHER_ERROR` and the thrown value on `cause`.

The page the link opens:

```vue [pages/sign-in-with-link.vue]
<script setup lang="ts">
import { api } from '~~/convex/_generated/api'

const route = useRoute()
const state = useSignInWithEmailMagicLink(api.auth, {
  emailCode: () => String(route.query.code),
})

watch(state, async ({ status }) => {
  if (status === 'complete') await navigateTo('/')
})
</script>

<template>
  <p v-if="state.status === 'loading'">Signing in…</p>
  <p v-else-if="state.status === 'error'">This link cannot be used: {{ state.userError.error }}</p>
</template>
```

A link works once, for ten minutes, and only in the browser that asked for it, as [above](#sign-in-with-an-email-and-password). Asking again replaces the earlier request's secret, so only the newest link works: an older one gives `INCORRECT_CODE`. A link opened in another browser, or opened again after it signed the visitor in, gives `MISSING_SECRET`. An expired link gives `INVALID_CHALLENGE`.

With [cookie sessions](#cookie-sessions-and-server-rendering), list `signInWithEmailMagicLink` in `signIn`. `sendEmailMagicLink` does not start a session and is not listed.

On the Convex side, `setupEmailMagicLink` takes the email component, the Resend sender and the `url` of the page the link opens.

## Sign in with Google, Apple, GitHub or Discord

Each provider has one composable. `signIn()` sends the visitor to the provider, and the provider sends them back to the page they left:

```vue [pages/login.vue]
<script setup lang="ts">
import { api } from '~~/convex/_generated/api'

const { signIn } = useSignInWithGithub(api.auth)
const { flowError } = useOauth()
</script>

<template>
  <button @click="signIn()">Sign in with GitHub</button>
  <p v-if="flowError">Sign-in failed: {{ flowError.error }}</p>
</template>
```

`useSignInWithGoogle`, `useSignInWithApple` and `useSignInWithDiscord` have the same shape. Discord needs `@convex-dev/auth` 2.1 or newer. Pass `signIn({ redirectTo })` to return to another page.

The sign-in finishes on the page the visitor returns to, with nothing in your code waiting for it. So a failure after the return shows up in `useOauth().flowError`, a ref that is `null` when there is none:

| `flowError.error` | Meaning |
| --- | --- |
| `ACCESS_DENIED` | The visitor cancelled at the provider. |
| `EXPIRED` | The sign-in took too long, or its code was already used. |
| `INVALID_FLOW` | This browser did not start the sign-in, or has already finished it. |
| `OTHER_ERROR` | Anything else. The thrown value is on `cause`. |

A failure to start comes back from `signIn()` itself, as `{ status: 'error', userError }`.

Return to a page that is not behind the [`convex-auth` middleware](#protect-a-page). The visitor has no session yet when they come back, so a protected page would redirect them to the login page and drop the sign-in.

With [cookie sessions](#cookie-sessions-and-server-rendering), list each provider's `completeSignInWith…` function in `signIn`. Its `startSignInWith…` function is not listed.

## Sign in with a passkey

One composable drives the login form. There is nothing more to install: the passkey dialogs run on `@simplewebauthn/browser`, which `@convex-dev/auth` already depends on. The visitor types a username, and `signIn` signs them in with their passkey, or creates the account with a new one when the username is free:

```vue [pages/login.vue]
<script setup lang="ts">
import { api } from '~~/convex/_generated/api'

const { signIn, pending } = useSignInWithUsernamePasskey(api.auth)
const username = ref('')
const error = ref<string | null>(null)

async function onSubmit() {
  const result = await signIn({ username: username.value })
  error.value = result.status === 'error' ? result.userError.error : null
}
</script>

<template>
  <form @submit.prevent="onSubmit">
    <input v-model="username" name="username" autocomplete="username webauthn" required :disabled="pending">
    <button type="submit" :disabled="pending">Continue with a passkey</button>
    <p v-if="error">{{ error }}</p>
  </form>
</template>
```

`signIn` never throws. A completed result carries `flow`: `'signUp'` when it created the account, `'signIn'` when it used an existing one. A closed dialog arrives as `userError.error === 'CEREMONY_ABORTED'`, and a second call while the first still runs as `'ALREADY_PENDING'`, which needs no message.

`autocomplete="username webauthn"` turns on passkey autofill. While the component is mounted, the browser lists the visitor's passkeys among the field's suggestions, and picking one signs them in with no submit. The composable also returns `autofill`, three refs that follow that request:

| Ref | Value |
| --- | --- |
| `autofill.available` | `true` when the browser can list passkeys, `false` when it cannot, `null` while it checks. |
| `autofill.status` | `'idle'`, `'waiting'` for a pick, `'signingIn'`, `'signedIn'`, or `'stopped'` after a failure. |
| `autofill.lastError` | The last failure, or `null`. |

A signed-in user manages their passkeys with two more composables. Both ask for an existing passkey first, so a user with one passkey adds a second before they can remove either:

```vue [components/PasskeySettings.vue]
<script setup lang="ts">
import { api } from '~~/convex/_generated/api'

const list = useQuery(api.auth.listPasskeys, {})
const { addPasskey, pending: adding } = useAddPasskey(api.auth)
const { removePasskey, pending: removing } = useRemovePasskey(api.auth)
</script>

<template>
  <ul v-if="list?.success">
    <li v-for="passkey in list.passkeys" :key="passkey.passkeyId">
      {{ passkey.name ?? 'Unnamed passkey' }}
      <button :disabled="removing || list.passkeys.length < 2" @click="removePasskey(passkey.passkeyId)">Remove</button>
    </li>
  </ul>
  <button :disabled="adding" @click="addPasskey()">Add a passkey</button>
</template>
```

`addPasskey()` and `removePasskey(id)` resolve to `{ success: true }` or `{ success: false, userError }`. Renaming needs no composable: call `useMutation(api.auth.renamePasskey)`.

On the Convex side, `setupUsernamePasskey` takes the `rpId` and `origin` of your site. A passkey is bound to its `rpId` for good, so set the production domain before the first real sign-up.

With [cookie sessions](#cookie-sessions-and-server-rendering), list `finishSignInWithUsernamePasskey` and `finishSignUpWithUsernamePasskey` in `signIn`. The other passkey functions are not listed.

For passkey dialogs that do not come from the browser, such as a native passkey library, `createUsernamePasskeyHooks(ceremonies)` from `nuxt-convex-module/convex-auth/methods/username-passkey/custom` makes the same three composables on your own ceremonies. That entry does not import `@simplewebauthn/browser`.

## Sign out, and the access token

```ts
const { signOut, setSession } = useAuthActions()
const token = useAuthToken()
```

`signOut` revokes the session on the server and clears it in the browser. `setSession` adopts the tokens a sign-in mutation returned, for a sign-in you run yourself. `useAuthToken()` is a ref of the current access token, or `null` when signed out. Send it as `Authorization: Bearer …` to your own Convex HTTP actions and nowhere else.
