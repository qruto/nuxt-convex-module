This page collects everything the module does for your app's security, everything it deliberately leaves to you, and the sharp edges worth knowing before you deploy.

The short version: install [`nuxt-security`](https://nuxt-security.vercel.app) and the module wires it up with Convex-aware defaults. Without it, the module still hardens its own surfaces — the auth proxy, SSR payloads, cross-domain tokens — but your app ships without security headers.

```bash
npm i nuxt-security
```

## What ships hardened

| Surface | Default | Opt out |
|---|---|---|
| [Content Security Policy](#content-security-policy) | Convex origins added to `connect-src` (production), `img-src`, `media-src` | `convex.security: false` |
| [Auth proxy caching](#the-better-auth-proxy) | `cache: false`, `prerender: false` | app `routeRules` |
| [Auth proxy XSS validator](#why-the-xss-validator-is-off-there) | off for that route — it rejects valid credentials | app `routeRules` |
| [Auth proxy methods](#the-better-auth-proxy) | `GET`, `HEAD`, `POST`, `OPTIONS` only | app `routeRules` |
| [Authenticated SSR responses](#auth-tokens-in-ssr-payloads) | `Cache-Control: private, no-store` | set the header yourself later in the request |
| [Post-sign-in redirects](#post-sign-in-redirects) | `resolveAuthRedirect()` helper (you must use it) | — |
| [Cross-domain one-time tokens](#cross-domain-one-time-tokens) | unrestricted, matching upstream | `betterAuth.crossDomainCallbackRoute` opts **in** to the guard |

Everything above is applied through standard Nuxt mechanisms — route rules and the `security` config key — so anything you set yourself wins.

## Content Security Policy

A CSP tells the browser which origins a page may load from and talk to. `nuxt-security` ships a strong baseline; what it cannot know is where *your* Convex deployment lives. The module fills that in.

When `nuxt-security` is installed, the module registers it as a module dependency — you don't add a `modules` entry, and if you do list it yourself, Nuxt dedupes — then extends its CSP:

| Directive | Added | When |
|---|---|---|
| `connect-src` | deployment origin over `https:` and `wss:`, plus the `.site` origin when `siteUrl` is set | production only |
| `img-src` | deployment and `.site` origins | always |
| `media-src` | deployment and `.site` origins | always |

`connect-src` covers the realtime WebSocket, one-shot HTTP queries, and the direct-to-Convex file uploads. `img-src` / `media-src` cover files served from Convex storage through `useStorageUrl()`.

The origins are appended at **runtime**, from `runtimeConfig.public.convex`, through nuxt-security's `nuxt-security:routeRules` hook. Two consequences worth having: the deployment URL can come from the environment at deploy time rather than being baked into the build, and the position of `nuxt-security` in `modules` doesn't matter.

### Why `connect-src` is production-only

In development the module leaves `connect-src` untouched. Vite's HMR socket and the Nuxt DevTools channel run on their own ports, which `'self'` does not cover — materializing the directive would break both. `nuxt-security`'s own default leaves it unset, so dev keeps that behaviour and production gets the tightened one.

The practical consequence: **a CSP mistake surfaces only after `nuxt build`.** Check a production preview before you ship.

### Adding your own origins

This is the part most apps need. The module *creates* `connect-src` where nuxt-security left it open, so anything else your browser code talks to must be named — an auth provider, analytics, error reporting, your own API. Your entries are preserved and the Convex origins are appended to them:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-convex-module'],
  security: {
    headers: {
      contentSecurityPolicy: {
        // The Convex origins are appended to whatever you put here.
        'connect-src': ['\'self\'', 'https://your-tenant.auth0.com'],
      },
    },
  },
})
```

::note
[Better Auth](/components/better-auth) needs nothing here: its traffic goes through the same-origin `/api/auth/**` proxy, so `'self'` already covers it. [Clerk](/components/clerk) and [Auth0](/components/auth0) call their provider directly from the browser, so their origins must be listed. Use the exact frontend-API or tenant domain from your provider's dashboard — including custom domains.
::

### Opting out

`convex: { security: false }` leaves nuxt-security's CSP entirely alone. Disabling nuxt-security itself (`security: false`) or just its CSP (`security.headers.contentSecurityPolicy: false`) also skips the Convex additions. In every case the rest of the module keeps working — you simply own the policy.

## The Better Auth proxy

With the [Better Auth](/components/better-auth) integration enabled, the module mounts a proxy at `authRoute` (default `/api/auth/**`) that forwards to your Convex `.site` URL. The design is deliberate: the browser only ever talks to **your own origin**, so session cookies stay first-party and no CORS relaxation is needed anywhere.

On the way out the proxy strips hop-by-hop headers (`transfer-encoding`, `content-length`, `connection`), pins `host` to the Convex site URL, and stamps the forwarding headers Better Auth uses to reconstruct the original request (`x-forwarded-host`, `x-forwarded-proto`, and their `x-better-auth-*` counterparts). On the way back it drops `content-encoding` / `content-length` — `fetch` has already decoded the body — and relays everything else verbatim, including each `Set-Cookie` and any `Location`.

The route carries these rules:

```ts
{
  cache: false,        // live session traffic is never cached
  prerender: false,    // and never visited by a prerender pass
  security: {
    xssValidator: false,
    allowedMethodsRestricter: { methods: ['GET', 'HEAD', 'POST', 'OPTIONS'] },
  },
}
```

Better Auth serves `GET` and `POST` only, so anything else is a probe and is refused with a `405` before it reaches your deployment — which also means it costs you nothing.

### Why the XSS validator is off there

This one is a correctness fix, not a preference. `nuxt-security`'s XSS validator HTML-escapes the JSON request body and answers **`400 Bad Request`** if escaping changed anything. Applied to auth traffic that rejects legitimate input:

```json
{ "email": "a@b.com", "password": "p<ssw0rd!" }   // 400 — the `<` was escaped
{ "name": "O<Brien" }                              // 400
```

A password is an opaque secret forwarded to an auth server; it is never HTML this app renders, so escaping it protects nothing and breaks sign-in and sign-up for anyone whose password contains `<` or `>`. The validator stays on for every other route.

::caution
If you mount your own auth-adjacent server routes that accept passwords or free text, they need the same exemption — `routeRules: { '/api/my-route': { security: { xssValidator: false } } }`. Otherwise strong passwords are silently rejected with a `400`.
::

### Rate limiting

`nuxt-security` rate-limits **every** route by default — 150 requests per 5 minutes per IP — and that includes the auth proxy. The module does not override it: any limit tight enough to meaningfully slow credential stuffing is also tight enough to break session polling for users behind a shared IP, and only you know your traffic. Tune it per route if you want something different:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  routeRules: {
    '/api/auth/**': {
      security: { rateLimiter: { tokensPerInterval: 60, interval: 60_000 } },
    },
  },
})
```

::caution
The limiter identifies clients by `X-Forwarded-For` when present, and trusts it unconditionally. Behind a proxy or CDN that **overwrites** the header this is correct; exposed directly to the internet, any client can spoof the header and bypass the limit. Terminate traffic behind a proxy you control.
::

Better Auth applies its own rate limiting on the Convex side. The Nitro-side limit is defence in depth, and protects your deployment's usage bill from being run up through the proxy.

## Auth tokens in SSR payloads

To avoid an auth round-trip on first paint, the server plugin prefetches the Convex JWT and passes it to the client through Nuxt state — mirroring how the React integration hands `initialToken` to its provider. That token, and any data from `preloadAuthQuery`, is serialized into the HTML as `window.__NUXT__`.

**The rendered page therefore contains a per-user bearer token.** The module sets

```
Cache-Control: private, no-store
```

on any response where a token was prefetched, so a CDN or shared proxy can never replay one user's page to another. It is set early enough that a route with different needs can still override it.

What this means for you:

- Don't relax that header on authenticated routes, and don't put authenticated pages behind a shared cache or ISR/SWR rule.
- Prerendering an authenticated page is a mistake — the token would be baked into a static file.
- Treat the payload as user-visible. Return only what the page renders from `preloadAuthQuery`; anything else is disclosed to the browser.

## Post-sign-in redirects

The `auth` route middleware sends unauthenticated visitors to your login page with the original destination attached:

```
/login?redirect=/dashboard
```

The middleware only ever writes a router path there, but that query is part of a URL **anyone can craft**. A login page that navigates to it verbatim is an open redirect — a phishing primitive on your own domain:

```vue
<!-- Vulnerable: /login?redirect=https://evil.example sends the user off-site -->
await navigateTo(route.query.redirect as string)
```

Use `resolveAuthRedirect()`, which is auto-imported alongside `useAuth`. It returns the destination only when it is a same-origin path, and the fallback otherwise:

```vue [pages/login.vue]
<script setup lang="ts">
const route = useRoute()
const { signIn } = useAuth()

async function onSubmit() {
  await signIn.email({ email, password })
  // '/dashboard' survives; 'https://evil.example' becomes '/'.
  await navigateTo(resolveAuthRedirect(route.query.redirect))
}
</script>
```

It rejects absolute URLs, scheme-relative `//evil.example`, backslash forms like `/\evil.example`, non-HTTP schemes, and a repeated `?redirect=` (which arrives as an array — ambiguous, and an attacker picks the entry you didn't mean). It also rejects paths that *normalize* into a protocol-relative URL: `/..//evil.example` starts with a single slash but resolves to `//evil.example`, so the guard validates the serialized result, not just the input. Pass your own fallback as the second argument: `resolveAuthRedirect(route.query.redirect, '/home')`.

## Cross-domain one-time tokens

Only relevant if your auth client installs `crossDomainClient()`.

When sign-in completes on a different origin, Better Auth redirects back with a `?ott=` one-time token that the client exchanges for a session. The protocol **cannot bind that token to the browser that started the flow** — magic-link flows legitimately finish in another browsing context — so anyone holding a fresh token can craft a link that signs its visitor into *their* session. That's login CSRF: the victim ends up authenticated as the attacker, and anything they then do lands in the attacker's account.

Upstream consumes the token on whatever page it lands on. This module lets you restrict it to the one route your sign-in `callbackURL`s point at:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  convex: {
    betterAuth: { crossDomainCallbackRoute: '/auth/callback' },
  },
})
```

With it set, a token arriving anywhere else is stripped from the URL but never exchanged. It is **off by default** to preserve upstream parity — turn it on if you use cross-domain auth.

## File storage

Uploads from `useUpload()` / `useUploadQueue()` go straight from the browser to the one-time URL your `generateUploadUrl` mutation returns. They never pass through Nitro, which has two consequences:

- `nuxt-security`'s request-size limiter (2 MB, or 8 MB for multipart) does **not** apply to them. Enforce size and content-type limits in your Convex function, and validate the stored file server-side rather than trusting the browser.
- The upload origin must be allowed by `connect-src` — the module's CSP already covers it.

Files read back through `useStorageUrl()` are served from the deployment origin, which is why `img-src` and `media-src` include it. Those URLs are signed and time-limited but otherwise unauthenticated: anyone holding one can fetch the file. Gate the *query* that hands out the URL, and don't embed storage URLs in anything cacheable by a shared proxy.

## What `nuxt-security` gives you beyond the CSP

Installing it brings a good deal the module doesn't have to configure. Defaults worth knowing:

| Protection | Default |
|---|---|
| `Strict-Transport-Security` | 180 days, `includeSubdomains` |
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` / `frame-ancestors` | `SAMEORIGIN` / `'self'` — clickjacking cover for your login page |
| `Referrer-Policy` | `no-referrer` |
| `Cross-Origin-Opener-Policy` | `same-origin` |
| `Cross-Origin-Embedder-Policy` | `credentialless` in production |
| `Permissions-Policy` | camera, microphone, geolocation, display-capture, fullscreen all denied |
| Request size limit | 2 MB (8 MB multipart) |
| Rate limit | 150 requests / 5 min / IP |
| `X-Powered-By` | removed |
| Subresource integrity | on for bundled assets |

::caution
**`security: { strict: true }` needs testing against Convex storage.** Strict mode raises `Cross-Origin-Embedder-Policy` to `require-corp`, under which every cross-origin subresource must send `Cross-Origin-Resource-Policy`. If Convex's storage responses don't, your images and media break. The default `credentialless` has no such requirement. Strict mode also sets `default-src 'none'`, so directives the module doesn't manage need filling in. Verify a production build before enabling it.
::

CSRF protection (`nuxt-csurf`) is **off** by default in nuxt-security. Better Auth carries its own CSRF defences for the auth routes; if you add your own state-changing endpoints, enable it or check origins yourself.

## Production checklist

1. **Install `nuxt-security`.** Without it there is no CSP and no security headers — the module's own hardening is only part of the picture.
2. **Check the CSP against a production build**, not `nuxt dev` — `connect-src` only exists in production.
3. **Add third-party origins** to `connect-src` (Clerk, Auth0, analytics, error reporting).
4. **Use `resolveAuthRedirect()`** on your login page. Never navigate to `route.query.redirect` directly.
5. **Set `crossDomainCallbackRoute`** if you use `crossDomainClient()`.
6. **Keep authenticated pages out of shared caches** and away from prerendering.
7. **Terminate behind a proxy that overwrites `X-Forwarded-For`**, or the rate limiter is bypassable.
8. **Enforce upload limits in your Convex functions** — direct-to-Convex uploads skip Nitro's limiter.
9. **Set `NUXT_PUBLIC_CONVEX_SITE_URL`** to the `.site` domain. The module errors on a `.convex.cloud` value here, but a wrong custom domain is silent.
10. **Keep dependencies current.** The repository runs Dependabot with a release-age cooldown; do the same in your app.

## Reporting a vulnerability

Found something in this module? Report it privately through [GitHub Security Advisories](https://github.com/qruto/nuxt-convex-module/security/advisories/new) — not a public issue. The full policy, including scope and response times, is in [SECURITY.md](https://github.com/qruto/nuxt-convex-module/blob/main/SECURITY.md).

Issues in Convex, Better Auth, Polar, or Resend themselves belong to those projects' security processes. If you're unsure which side a finding lands on, report it here and it will be routed.
